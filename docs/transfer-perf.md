# Airpipe 文件传输性能研究：压缩、分块与并行

**目的**：回答四个问题——①压缩能否提速？②分块多大合适、能否自适应？③并行分块能否显著提速？④有没有成熟库直接解决？先摸清现状（§1），定量测试（§3–§5），最后给 v2 建议（§7）与调研（§8）。

> 测试日：2026-11-05。环境见 §2。复现命令见 §8。

---

## 1. 现状：传输模型代码级梳理

### 1.1 总体架构

- **单条 TCP + TLS 1.3 连接**，手机永远是客户端（主动出站），PC 监听（`docs/protocol.md` §1）。剪贴板帧与文件帧在同一条连接上双向复用。
- **协议层分块**：文件切成 **128 KiB** 的 `D` 帧（`CHUNK = 131072`，PC `pc/src/proto.rs:8`，Android `Proto.kt:15`）。TLS 1.3 单条应用数据记录上限 16 KiB（RFC 8446 固有），所以一个 128 KiB 帧在线上是 8 条 TLS 记录——**调大分块也改变不了线上记录粒度**。
- **可靠性锚点**：发送方边发边算 sha256，整文件发完后接收方回 `F`（FILE_RESULT）附整文件 sha256；不符则**整文件重发一次**（protocol.md §6）。

### 1.2 「串行」到底串行在哪——两层必须分开

「分块串行、前一块阻塞后一块」的印象**部分正确**，实际有两层：

| 层 | 行为 | 证据 |
| :--- | :--- | :--- |
| **单文件内部（块间）** | **不阻塞**。`D` 帧连续写入，靠 TCP 流控背压，无逐块 ACK | PC `daemon.rs:1159-1165`：`while let Some(chunk) = fc.next()` 一路 `conn.send(FileData)`；Android `SyncService.kt:586-600` 同样一口气循环写 |
| **文件之间（文件级）** | **严格停止-等待（stop-and-wait）**。文件 N 的 `F` 不回来，文件 N+1 一个字节都不会发 | PC `daemon.rs:1169`：`conn.wait_result(id, 600s)` 阻塞泵线程；Android `SyncService.kt:610`：`future.get(120s)` 阻塞 writerLoop |

同方向一次只跑一个传输（protocol.md §6），泵单线程（`daemon.rs:1011`）。稳态时序：

```
[B 帧][D×n][E 帧] ──等 F（尾包在途 + 1×RTT + 接收方 flush/rename/sha 收尾）──> [下一文件]…
```

**这是现状模型最主要的性能病灶**——§4 实测小文件场景约一半时间耗在等 `F`，远比块大小和压缩重要。

### 1.3 每块的用户态成本（现状的隐性浪费）

- PC 发送：`conn.send(&Frame::FileData { data: chunk.to_vec() })` **每块克隆一次 128 KiB**（`daemon.rs:1160-1163`），`Frame::encode` 再拼一个帧缓冲。
- Android 发送：每块新建 `ByteArray(4+n)` 拼载荷，逐帧过 `synchronized(sendLock)`。
- Android 接收：整帧进内存 → FUSE 写盘 + sha256 增量；PC 接收：`BufWriter<File>`（默认 8 KiB 缓冲）+ sha256。

§3.1 证明这套栈上限 ≈ 2.6 GB/s，**当前网络（实测 1.3–4.2 MB/s）下有 600 倍余量，以上浪费无感**。

### 1.4 与传输效率相关的既有常量

| 常量 | 值 | 备注 |
| :--- | :--- | :--- |
| `CHUNK` | 128 KiB | 双端硬编码，不可配 |
| `PROGRESS_EVERY` | 4 MiB | 进度帧频率，与流控无关 |
| 无压缩、无并行、无断点续传 | — | v1 刻意从简 |

## 2. 测试环境与方法

### 2.1 硬件与网络拓扑

```
PC (Ryzen 7840H 16核, Arch, rustls 0.23/ring)
 ├─ enp3s0f3u4 (USB2 RNDIS → ZTE 上网卡通棒, 192.168.0.178)──┐
 │                                                            ├─ 同一 L2：棒自带 WiFi ← 手机 wlan0 (192.168.0.143)
 ├─ enp3s0f3u2 (USB2 RNDIS → 手机 USB tether, 10.110.82.154)──手机 rndis0 (10.110.82.2)
 └─ wlp1s0 (校园网, 与手机不通, 不参与)
手机: Xiaomi 2312DRA50C (garnet) / Android 16 / Airpipe 1.0.1 (debug)
```

- **「WLAN 路径」**：PC →USB→ 棒 →WiFi(2.4G)→ 手机（PC 侧也有 USB 腿，这是本机真实环境）。
- **「USB 路径」**：直连手机 rndis0；adb 同在 USB2 总线（仅控制流量）。

### 2.2 空载 RTT（ping）

| 路径 | RTT avg | 备注 |
| :--- | :--- | :--- |
| WLAN（手机灭屏） | **117 ms** | 手机 WiFi 省电模式（PSM），beacon 量级；传输中会自唤醒（§4 实测有效 RTT 更低） |
| USB（rndis） | 1.4 ms | |

### 2.3 方法

- **A 组（真实 App）**：PC→手机：daemon 前台 `-v`，stderr 经时间戳管道落盘，t₀=发送指令前、t₁=第 N 条 `sent` 日志到达（每条 `sent` 均为 sha256 核对通过的端到端完成）。手机→PC：`adb shell am start … --eu android.intent.extra.STREAM file:///sdcard/…`（实测 `--eu` 可传 Uri，App 有所有文件权限可读 file://），t₁=daemon 的 `done` 日志。
- **B 组（裸 TCP）**：`dd | ncat` ↔ `toybox nc`，手机侧 `> /dev/null`；4 流=4 对独立连接。
- **C 组（栈回环）**：新增 `pc/src/bin/tlsbench.rs`，127.0.0.1 上复刻 daemon 帧写入路径（同款 rustls 记录 flush 循环），扫分块 × TLS/明文 × 流数。
- **D 组（压缩）**：PC `zstd -b`（1.5.7）；手机 toybox `gzip -dc` 计时；端到端用「压成 .zst 再走 App」实测。
- 路径归属用 `ap status` 的手机源 IP 验证；WiFi 速率有 ~15% 漂移，结论只取相邻运行对比。

## 3. 定量结果

### 3.0 先决发现：USB tethering 对 App 完全不可用（问题②的前置）

比性能更重要的发现——**airpipe v1 架构上就走不了 USB 网线共享**：

1. 手机侧 `ip route get 10.110.82.154`（PC 的 tether 地址）解析为 **经 wlan0 → 棒**；把 WiFi 关掉则变为**经蜂窝 rmnet**。Android 把 tether 子网放独立路由表，App 主路由表永远不指向 rndis0——手机出站连接**物理上进不了 USB 线**（协议要求手机主动出站，正中死穴）。
2. 反方向 PC→手机：rndis0 上的新入站 TCP 被 HyperOS 防火墙丢弃（实测超时；ICMP 放行）。tether 的设计意图是「手机当路由器给 PC 供网」，不是对等互联。
3. USB 数据线的现实通道只有 **adb**：`adb reverse tcp:17580 tcp:17580` + App 拨 `127.0.0.1`。需要 App 加一个「USB 模式」开关（改动很小，见 §6 建议 ⑤）。

### 3.1 C 组：用户态栈回环基准（tlsbench，127.0.0.1，1 GiB/组）

| 模式 | 分块 | 流数 | 吞吐 |
| :--- | :--- | ---: | ---: |
| TLS 1.3 | 16 KiB | 1 | **3187 MB/s** |
| TLS 1.3 | 64 KiB | 1 | 2692 MB/s |
| TLS 1.3 | **128 KiB（现状）** | 1 | 2609 MB/s |
| TLS 1.3 | 512 KiB | 1 | 2768 MB/s |
| TLS 1.3 | 1 MiB | 1 | 2793 MB/s |
| TLS 1.3 | 128 KiB | **4** | 8899 MB/s（栈随核近线性扩） |
| 明文 TCP | 16 KiB | 1 | 3381 MB/s |
| 明文 TCP | 128 KiB | 1 | 3278 MB/s |
| 明文 TCP | 1 MiB | 1 | 3558 MB/s |

**结论（问题②）**：分块 16 KiB→1 MiB 吞吐都在 2.6–3.2 GB/s 平台期（±15%，16 KiB 还略快），TLS 相对明文仅 ~20% 代价。真实链路 1.3–4.2 MB/s，**栈余量 600 倍以上——128 KiB 分块不是瓶颈，自适应分块没有收益空间**。单连接已达单核加密极限，但那远在需求之上。

### 3.2 B 组：裸 TCP 链路容量

| 测量 | 结果 | 说明 |
| :--- | :--- | :--- |
| WLAN PC→手机 1 流 | **4.19 MB/s（33 Mbps）** | 128 MiB / 30.6 s |
| WLAN PC→手机 4 流 | 3.95 MB/s（32 Mbps） | **并行 0 收益**：瓶颈是空口+PSM，不是单流 |
| WLAN 负载下 RTT | avg 131 ms / max 496 ms | 空载 117 ms 相当 |
| USB adb push 256 MiB | **36.3 MB/s（290 Mbps）** | USB2 实际水位，双向对称（pull 36.9） |
| USB RNDIS 直连 | 双向阻断 | §3.0 |

### 3.3 A 组：真实 App 端到端（WLAN 路径，256 MiB 语料）

| 场景 | 耗时 | 有效吞吐 | 相对裸 TCP |
| :--- | ---: | ---: | ---: |
| rand-256M（单大文件，灭屏） | 90.0 s | **2.84 MB/s** | 68% |
| rand-256M（复跑） | 88.7 s | 2.89 MB/s | 69% |
| rand-256M（**亮屏**） | 142.4 s | 1.80 MB/s | — |
| text-256M 原样 | 103.9 s | 2.46 MB/s | — |
| **text-256M 先 zstd-1** | **35.4 s** | 1.96 MB/s（按原始字节） | — |
| rand-256M 先 zstd-1 | 103.8 s | 2.47 MB/s | ≈原样（比率 1.000） |
| med：256×1 MiB | 113.5 s | 2.26 MB/s | — |
| small：1024×128 KiB | 101.2 s | **1.27 MB/s** | — |
| **手机→PC** rand-256M | 165.1 s | 1.55 MB/s | — |

要点：

- **App 协议栈吃掉裸 TCP 的 ~32%**（TLS 记录封装、sha256、FUSE 落盘、每文件停止等待）。
- **压缩端到端 2.94×**（103.9→35.4 s，相邻运行消除漂移）；对不可压内容无损失。
- **小文件崩塌**：同样 128 KiB/文件的量级，吞吐掉到 1.27 MB/s（§4 解剖）。
- **亮屏反而更慢**（1.80 vs 2.84 MB/s）：实测现象，未定位根因（亮屏引入的射频/调度策略变化），灭屏常驻服务恰是本 App 的常态使用方式，故未深究。
- **方向不对称**：手机发（JVM/FUSE 读+手机上行）比 PC 发慢 1.8×。

### 3.4 D 组：压缩

**PC 压缩**（zstd 1.5.7 单线程）：text（源码+man 页）`-1` 比率 **3.707** @ **454 MB/s**；urandom 比率 1.000 @ 4828 MB/s（近似直通）。
**手机解压**（toybox gzip -dc，text 80.6→256 MiB）：1.02 s ≈ **250 MB/s**；zstd 解压比 gzip 快 3–5×，两种链路下都远快于网络，接收端不构成瓶颈。

**交叉点**：压缩有收益 ⟺ `S/C + S·r/R < S/R` ⟺ **压缩速率 C > R/(1−r)**：

| 链路 R | r=1.05（已压媒体） | r=2 | r=3.7（文本） |
| :--- | :--- | :--- | :--- |
| WLAN 2.8 MB/s | C>59 MB/s ✅ | C>3.1 ✅ | C>1.0 ✅ |
| USB 36.5 MB/s | C>730 MB/s ⚠️接近线 | C>36.5 ✅ | C>13.3 ✅ |

**结论（问题①）**：慢链路上压缩几乎稳赚（文本实测 2.94×）；快链路上文本仍大赚、已压缩媒体刚好踩线（zstd-1 对不可压数据近乎免费，实测端到端无损失，但也没收益）。**应当按内容判定**：`.jpg/.mp4/.zip/.apk/…` 白名单跳过，其余 zstd -1（或先压 4 MiB 探针，比率>1.2 才全压）——同 Syncthing 的 NEVER/METADATA/ALWAYS 三档思路。

## 4. 小文件停止等待解剖（问题③核心证据）

从 daemon 日志逐文件到达时间戳提取周期（消除 WiFi 漂移看分布）：

| 场景 | 每文件周期（中位） | 纯线时间 @2.85 MB/s | **暴露的每文件开销** | 开销占比 |
| :--- | ---: | ---: | ---: | ---: |
| 1 MiB × 256 | 437 ms | 364 ms | ~73 ms | 17% |
| 128 KiB × 1024 | **93 ms** | 45 ms | **~48 ms** | **52%** |

- **小文件场景一半墙钟时间在等 `F`**（尾包在途 + RTT + 接收方 flush/rename/sha 收尾），纯线时间只占 48%。
- 周期内开销（~48 ms）小于空载 RTT（117 ms）：连续传输使 PSM 保持唤醒、有效 RTT 收缩——但即便如此等待仍占半壁。
- 若发送端改为**窗口=4 的文件级流水线**（不必等 `F` 就开始下一文件），小文件吞吐理论上限 ≈ 纯线速率 2.85 MB/s → **~2.2× 提速**；1 MiB 文件 ~1.2×；单大文件 0（本就不等）。
- USB 场景（若打通 adb 通道）：RTT 毫秒级、速率 12 倍，每文件开销占比 <5%，流水线收益趋近于零——**该优化只对高 RTT 慢链路（WiFi/互联网）有价值**。

## 5. 并行分块能救什么、不能救什么（问题③）

「同时 4 个分块在传」在两条链路上分别被数据否定/限缩：

1. **同一文件的并行分块（条带化）**：收益前提是单 TCP 流填不满链路。实测 WLAN 上 4 条并行 TCP 的聚合 = 单流的 95%（空口+PSM 是瓶颈，不是单流窗口），USB 是 USB2 物理上限——**条带化在这两条链路上都无增益**，只增加协议复杂度（D 帧需带偏移、乱序重组、部分重传语义）。
2. **并行文件（多条目同时在途）**：这就是 §4 的窗口化流水线，是**有实测支撑的正确形态**（小文件 2.2×）。且实现代价意外地小——见下。
3. **多 TCP/QUIC 连接**：WLAN 无收益（B 组），且违背「单连接双向复用、手机出站」的架构约束（HyperOS 杀入站）。用户可配的「并行度」参数应落在这层：**`[transfer] window = 4`（默认 4，可配 1..8）**。

> **关键实现洞察**：v1 的**接收端已经按 id 多路复用**（PC `daemon.rs:633` `HashMap<u32, Inbound>`；Android `SyncService.kt:649` `transfers` map，B/D/E/F 乱序混排都能正确处理——协议本身从未禁止）。停止等待纯粹是**发送端**的自觉行为。把 `wait_result` 从「阻塞泵线程」改成「窗口未满则继续入队」是单侧改动，协议无需动一个字节。

## 6. 结论与 v2 建议（按实测收益排序）

| # | 改动 | 实测/推算收益 | 代价 |
| :--- | :--- | :--- | :--- |
| ① | **发送端文件级流水线窗口**（`window` 配置，默认 4）——**已实现（v2）** | 小文件 ~2.2×（WLAN）；大文件不变 | 小：仅发送端两处循环改造；sha 校验/重发语义不变 |
| ② | **zstd -1 传输前压缩** + 已压缩扩展名白名单——**已实现（v2）** | 文本/文档 2.9×（WLAN 实测）；USB 上 ~3×；不可压内容无损 | 小：PC 加 zstd crate（或 flate2），Android 加 zstd-jni/纯 Kotlin 帧级解压；B 帧加 1 bit 压缩标志 |
| ③ | **分块保持 128 KiB，不做自适应** | —（已证明非瓶颈，16 KiB–1 MiB 同速） | 零 |
| ④ | **不做单文件条带化/多连接并行** | —（两条链路均无增益） | 省掉大协议手术 |
| ⑤ | **USB 模式 = adb reverse**：App 设置里加「通过 USB(adb) 连接」开关，拨 127.0.0.1:17580（PC 侧 `adb reverse tcp:17580 tcp:17580` 自动或文档化） | 解锁 36 MB/s（12× WLAN）链路 | 小；这是 USB 数据线唯一可行通道（§3.0） |
| ⑥ | 顺手项：去掉 `chunk.to_vec()` 每块克隆；`BufWriter` 给 256 KiB | 微（栈余量 600×） | 极小 |

「给用户一个可配并行参数（默认 4）」的想法**方向正确但落点应调整**：不是「一个文件的 4 个分块并行」（无增益），而是「4 个文件同时在途」（有 2.2× 实测增益，且就是 ①）。

## 7. 成熟库/方案调研（问题④）

不是新问题。同类工具全部踩过这批坑，方案分四类：

| 方案 | 做法 | 对 Airpipe 的启示 |
| :--- | :--- | :--- |
| **Syncthing BEP** | 单 TLS 连接 + **流水线化块请求**（规范明言「无需等上一条的应答」），块 128 KiB–16 MiB，**每消息可选 LZ4**（NEVER/METADATA/ALWAYS） | 与建议 ①② 最同构的参照：连接不动，改窗口、加压缩档位即吃掉 RTT 与字节两重开销 |
| **iroh（n0）** | QUIC + BLAKE3 内容寻址 blob 传输，直连+中继兜底，**官方 Kotlin/Android 绑定** | 「换库全解决」的最短路径；代价是放弃现有 TLS 骨架与 60 KB 的自研协议，引入一大依赖 |
| **quinn（Rust QUIC）** | 一条 UDP 多 stream 复用、每 stream 独立流控、无跨流队头阻塞 | 若 v2 后仍不够（如未来跑多路径/外网），PC 侧成熟；Android 侧需 Cronet 或交叉编译 |
| **croc** | PAKE 加密、直连优先中继兜底、单流 + 断点续传 | 断点续传参照；并行上无作业可抄 |
| **Magic Wormhole** | 单条 transit TCP，规范自认大容量传输不足，并行多流留给未完成的「Dilated Wormhole」 | 反例佐证：单流+停止等待在高 RTT 链路的无力是公认问题 |
| **KDE Connect / LocalSend** | 每文件一条 TCP/HTTP POST，单流 | 「同类产品同样慢」的实证（localsend#384 等提速 issue 一堆） |
| **NFS `nconnect=N` / SMB3 Multichannel** | 内核级：N 条 TCP 摊一个会话 | 「并行=多连接摊带宽」的古老先例，专治单流填不满的**有线快网**——恰是我们两条链路都不缺的东西 |
| **HPN-SSH** | 加大 SSH 内部流控窗/免密模式，治高 BDP 慢 | 教训：**应用层自己的流控**（等价于 `wait_result`）常比 TCP 窗口更致命——正是 §4 实测 |
| **iperf3 `-P N`** | 多流测速是行业惯例 | 「单流测不准带宽」的行业共识本身即佐证 |

**回答**：有现成库（iroh 最完整、quinn 最通用），但没有一个能嵌进现有 TLS 骨架零成本解决——**收益最大的两刀（窗口流水线 + zstd）恰好都是协议内小改，不必引库**。若未来要跨外网/打洞/中继，再整体迁 iroh。

## 8. 复现

```bash
# 语料
head -c 268435456 /dev/urandom > rand-256M.bin          # 不可压
{ cat <repo文本源>…; zcat /usr/share/man/man*/*.gz; } ×6 | head -c 268435456 > text-256M.txt
zstd -1 -T0 text-256M.txt                                # 压缩收益语料

# C 组：栈回环（仓库内工具）
cd pc && cargo run --release --bin tlsbench -- --mib 1024            # 分块扫描
cargo run --release --bin tlsbench -- --mib 512 --streams 4 --tls    # 4流
```
